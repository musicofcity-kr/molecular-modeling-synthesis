# AI Control Core Constitution
## 적재적소 AI 통제와 좋은 결과물을 위한 핵심 운영 원칙

> 목적: AI를 무조건 강하게 묶는 것이 아니라, **위험한 부분은 정확하게 통제하고**, **품질 탐색이 필요한 부분은 자유도를 남겨** 더 좋은 결과물을 만드는 데 있다.

---

## 1. 최상위 원칙

개발의 중심은 기술이 아니라 **사용자 가치**다.

우선순위는 다음과 같다.

1. 사용자 가치
2. 정확성·안전성
3. 검증 가능성
4. 단순성
5. 유지보수성
6. 기술적 세련됨

> 하네스, 루프, 모듈, 멀티에이전트, 그래프는 모두 수단이다.
> 목적은 **좋은 제품**이다.

---

## 2. 개발 시작 전 반드시 정의할 5가지

### 2.1 Domain Goal
이 프로그램이 해결해야 할 실제 문제는 무엇인가?

### 2.2 Primary User
주 사용자는 누구인가?
- 학생
- 교사
- 연구자
- 관리자
- 일반 사용자

### 2.3 Primary Task
사용자가 반드시 성공해야 하는 핵심 작업 1~3개는 무엇인가?

### 2.4 Success Evidence
성공을 어떻게 판단할 것인가?
예:
- 처음 보는 사용자가 3분 안에 핵심 기능을 찾는다.
- 5분 안에 첫 작업을 완료한다.
- 결과 변화의 원인을 스스로 설명할 수 있다.

### 2.5 Non-Negotiables
절대 훼손되면 안 되는 것만 적는다.
예:
- 과학적 사실 오류 금지
- 학생 개인정보 노출 금지
- 핵심 데이터 손실 금지
- 핵심 기능 파손 금지

---

## 3. 요구사항 우선순위: P0~P3

### P0 — 반드시 지켜야 함
실패 시 배포 불가.
- 핵심 기능 실행
- 계산 정확성
- 개인정보 보호
- 데이터 손실 방지
- 핵심 흐름 유지

### P1 — 품질에 매우 중요
- 핵심 UX
- 모바일 사용성
- 접근성
- 성능
- 오류 메시지

### P2 — 있으면 좋은 개선
- 애니메이션
- 부가 기능
- 추가 통계
- 편의 기능

### P3 — AI 자율 탐색 영역
- 세부 레이아웃
- 미세 인터랙션
- 내부 구현 방식
- 시각적 연출

> 모든 항목을 P0로 만들지 않는다.

---

## 4. 정밀 통제 원칙

### 강하게 통제할 영역
- 과학적 계산
- 핵심 데이터 구조
- 인증
- 저장/삭제
- 개인정보
- 보안

### 자유도를 줄 수 있는 영역
- UI 구성
- 시각화 방식
- 인터랙션 표현
- 코드 리팩터링 방식
- 대안 UX 탐색

> 통제는 많이 하는 것이 아니라 **정확히 필요한 곳에만** 적용한다.

---

## 5. Control Budget

새로운 규칙을 추가하기 전 반드시 묻는다.

> 이 규칙이 없으면 실제로 어떤 실패가 발생하는가?

다음 4가지를 만족할 때만 규칙을 추가한다.
1. 실제 실패 경험이 있다.
2. 재발 가능성이 높다.
3. 실패 비용이 크다.
4. 판정 기준이 명확하다.

다음 유형의 규칙은 최소화한다.
- 단순 취향
- 과도한 파일 구조 강제
- 구현 방식 과잉 지정
- 중복 지침
- AI 탐색을 막는 사소한 형식 규칙

---

## 6. Evaluation Engineering

코드보다 먼저 **좋은 결과의 기준**을 만든다.

### E1 Correctness
기능이 정확한가?

### E2 Reliability
반복 사용해도 안정적인가?

### E3 Usability
처음 사용하는 사람이 스스로 사용할 수 있는가?

### E4 Domain Quality
해당 분야 목적을 실제로 달성하는가?

### E5 Product Quality
다시 쓰고 싶은 수준인가?

---

## 7. 증거 수준

- E3: 실제 실행/사용자 행동으로 확인
- E2: 자동 테스트 또는 브라우저 검증
- E1: 코드/문서 검토
- E0: 추정

> 핵심 기능은 가능하면 E2 이상,
> 중요 영역은 E3 또는 인간 검토를 우선한다.

## 8. 최소 그래프 원칙

기본 흐름은 이 정도면 충분하다.

```text
SPEC
  ↓
BUILD
  ↓
VERIFY
  ↓
EVALUATE
  ↓
USER TEST
  ↓
REPAIR
```

노드는 필요할 때만 추가한다.

---

## 9. 노드 판정

각 단계는 다음 중 하나로 끝난다.
- PASS
- RETRY
- REPAIR
- FALLBACK
- ESCALATE
- STOP

### PASS
성공 기준 충족

### RETRY
같은 방식 재시도 가능

### REPAIR
결함 수정 필요

### FALLBACK
안전한 대안으로 전환

### ESCALATE
인간 검토 필요

### STOP
즉시 중단해야 하는 위험 발생

---

## 10. 루프 원칙

루프는 무한 반복이 아니다.

반드시 다음을 둔다.
- 최대 재시도 횟수
- 최대 수정 범위
- 목표 점수 또는 개선 기준
- 회귀 여부 확인

좋은 루프는 다음과 같다.

```text
Baseline
↓
Change
↓
Measure
↓
Compare
↓
개선되었는가?
```

> “바뀌었다”와 “좋아졌다”를 구분한다.

---

## 11. 멀티에이전트 최소 원칙

멀티에이전트는 많을수록 좋은 것이 아니다.

권장 기본 구조:
- Builder
- Independent Reviewer
- 필요 시 Domain Validator 또는 UX Critic 추가

리뷰어는 개발자의 장황한 추론보다 아래만 본다.
1. 요구사항
2. 실제 결과물
3. 평가 기준
4. 테스트 결과

---

## 12. 사용자 테스트 우선

자동 테스트 PASS는 사용자 경험을 보장하지 않는다.

최소 사용자 테스트 질문:
- 처음 보는 사용자가 어디서 시작할지 아는가?
- 3분 안에 핵심 기능을 찾는가?
- 5분 안에 첫 작업을 완료하는가?
- 결과를 해석할 수 있는가?
- 막히는 지점이 어디인가?

교육용 프로그램 추가 질문:
- 오개념 위험이 없는가?
- 조작과 개념이 연결되는가?
- 학습 효과가 실제로 보이는가?

---

## 13. 과잉 엔지니어링 금지

다음 상황에서는 구조를 더 복잡하게 만들지 않는다.
- 핵심 기능이 아직 검증되지 않았다.
- 사용자 테스트가 없다.
- 기존 오류가 해결되지 않았다.
- 새 구조의 가치가 명확하지 않다.

> 사용자가 확인하지 않은 구조적 고도화는 후순위다.

---

## 14. Definition of Done

작업 완료의 최소 조건:
- [ ] 핵심 기능 실행
- [ ] P0 요구사항 충족
- [ ] 자동 테스트 통과
- [ ] 핵심 사용자 흐름 검증
- [ ] 회귀 없음
- [ ] 실제 화면 확인
- [ ] 남은 Known Issue 기록

교육용 프로그램 추가:
- [ ] 과학적 사실 검증
- [ ] 오개념 가능성 점검
- [ ] 학습 목표와 조작 연결

## 17. 한 줄 헌법

> **통제는 실패 비용이 큰 곳에 집중하고, 자유는 품질 탐색이 필요한 곳에 부여하며, 모든 판단은 실제 사용자 가치와 검증 가능한 증거를 기준으로 한다.**
